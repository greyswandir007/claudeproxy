# Протокол кэш-провайдеров (v1)

Общий HTTP-API, который реализуют кэш-провайдеры claudeproxy:
`claudeproxycachedb` (кэш точных повторов на БД). Прокси подключает
провайдеры по URL и общается с ними только этим протоколом. **Прокси ничего не знает о внутреннем
устройстве провайдера** — хранилище, уверенность, обучение и упаковка —
зона ответственности провайдера.

Термины: **lookup** — поиск готового ответа; **store** — запись пары
«запрос → ответ»; **feedback** — оценка ранее выданного ответа;
**answerId** — идентификатор выданного ответа у провайдера.

## Общие правила

- HTTP/JSON, UTF-8; тело ошибок — короткий текст.
- Провайдер не обязан поддерживать feedback (`{"applied": 0}` допустимо).
- **Управление хранилищем — самообслуживание провайдера**: сжатие,
  очистка, retention выполняются самим сервисом по своей политике (в т.ч.
  при длительном простое). Никаких команд обслуживания в протоколе нет.
- Прокси никогда не ждёт store (fire-and-forget) и ограничивает lookup
  таймаутом консультации (умолчание — `consult-timeout-milliseconds`,
  сейчас 1000 мс). При сбое/таймауте провайдера прокси молча уходит к
  провайдеру модели и пишет событие на дашборд (не чаще раза на backoff).
- `sessionKey` — стабильный идентификатор разговора (ключ разговора
  прокси). Провайдер волен использовать его как хочет (сессионные слои,
  корреляция); прокси лишь передаёт его во все вызовы разговора.

## Эндпоинты

### GET /v1/health

```json
{"status": "ok"}
```

### POST /v1/cache/lookup

Запрос:

```json
{
  "model": "claude-sonnet-5",
  "path": "/v1/messages",
  "requestHash": "sha256-канонического-тела",
  "requestJson": "{\"model\":...}",
  "sessionKey": "hex-строка, опционально"
}
```

`requestHash` считает прокси (SHA-256 канонического JSON без `stream`/
`metadata`). `requestJson` — оригинальное тело запроса; как извлекать из
него ключи/цепочки — дело провайдера.

Ответ при промахе: `{"hit": false}`.

Ответ при попадании:

```json
{
  "hit": true,
  "answerId": "произвольная строка провайдера",
  "responseFormat": "SSE" | "JSON",
  "responseBody": "тело для повтора (SSE-транскрипт или JSON ответа)",
  "confidence": 0.87,
  "inputTokens": 12345,
  "outputTokens": 200
}
```

- `confidence` (0..1) — уверенность провайдера в ответе. Точное
  совпадение (DB-кэш) — 1.0; вероятностные ответы — ниже. Прокси решает
  выдавать ли ответ по своему порогу `min-confidence`; низкая
  уверенность — не ошибка, просто обычный промах по сути.
- `inputTokens`/`outputTokens` — **оценка токенов, которые клиент не
  потратил** благодаря этому попаданию: их пишет в статистику прокси,
  не зная внутренностей провайдера. Точность — на совести провайдера
  (у DB-кэша — сохранённые при записи счётчики апстрима).

Прокси повторяет `responseBody` клиенту: SSE — как есть (или через
синтезатор для нестримового клиента), JSON — напрямую.

### POST /v1/cache/store

```json
{
  "model": "claude-sonnet-5",
  "path": "/v1/messages",
  "requestHash": "...",
  "requestJson": "...",
  "responseFormat": "SSE" | "JSON",
  "responseBody": "полный ответ апстрима (SSE-транскрипт или JSON)",
  "inputTokens": 12345,
  "outputTokens": 200,
  "sessionKey": "..."
}
```

`inputTokens`/`outputTokens` — счётчики из ответа апстрима: провайдер
сохраняет их, чтобы отдавать как оценку экономии при попаданиях. Ответ:
`{"stored": true}`.

### POST /v1/cache/feedback

Неявные оценки прокси (ошибка инструмента / регенерация → минус;
спокойное продолжение → плюс). Применяется только к ответам, которые
провайдер реально выдал (прокси помнит answerId по sessionKey).

```json
{"answerId": "...", "positive": true}
```

Ответ: `{"applied": 3}` — число затронутых записей (0 допустимо).

### GET /v1/cache/stats

Вся статистика кэша — на стороне провайдера; прокси только показывает:

```json
{
  "uptime_s": 3600,
  "counters": {
    "lookups": 120,
    "hits_exact": 40,
    "hits_probable": 5,
    "stores": 60,
    "feedback_positive": 5,
    "feedback_negative": 2,
    "tokens_saved_input": 480000,
    "tokens_saved_output": 9000
  },
  "latency_ms": {"lookup": {"p50": 1.0, "p95": 5.0, "p99": 12.0}},
  "extra": {}
}
```

- `hits_exact` — точные повторы; `hits_probable` — вероятностные ответы
  (меньше 1.0 confidence). Разделение обязательно: это разные классы
  надёжности.
- `tokens_saved_*` — сумма оценок экономии по попаданиям **за всё время**
  (провайдер персистирует счётчики сам).
- `extra` — свободное место провайдера под собственные показатели.
  Дашборд показывает обязательные счётчики и
  известные ключи `extra`.

## Поведение прокси

1. До роутинга: lookup у кэш-провайдера, выбранного для провайдера
   модели (встроенный `local` — умолчание).
2. Hit с `confidence >= min-confidence` → ответ клиенту без похода к
   провайдеру; usage-событие с оценкой токенов из ответа.
3. Miss → обычный путь; по завершении — store (со счётчиками апстрима).
4. Следующий запрос того же разговора → feedback по неявным сигналам,
   если предыдущий ответ был от кэша.

## Версионирование

Ломающие изменения — новой версией пути (`/v2/...`); расширения полей
ответа — обратно-совместимые (неизвестные поля игнорируются).
