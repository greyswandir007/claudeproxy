# Руководство по использованию

Повседневные сценарии работы с claudeproxy: подключение клиентов,
ключи, окна и лимиты, экономия токенов, дашборд. Быстрая настройка с
нуля описана в [quickstart.md](quickstart.md).

## Клиенты и подключение

Прокси говорит протоколом Claude (`/v1/messages`, стриминг, файлы) и
дополнительно принимает OpenAI-формат (`/v1/chat/completions`) —
подробности в [api.md](api.md).

Аутентификация — ключом клиента в любом из двух заголовков: `x-api-key`
или `Authorization: Bearer` (OpenAI SDK шлёт второй по умолчанию).

| Клиент | Что указать |
|---|---|
| Claude Code | `ANTHROPIC_BASE_URL=http://host:8080`, `ANTHROPIC_AUTH_TOKEN=cpk_...` |
| OpenAI SDK | `base_url="http://host:8080/v1"`, `api_key="cpk_..."` |
| Любой Anthropic-клиент | base URL прокси + `x-api-key: cpk_...` |

Список моделей, доступных клиентам, — `GET /v1/models`: имена `public`
из конфигурации провайдеров.

## Клиентские ключи

Ключ начинается с префикса `cpk_`. Заводить их можно двумя способами:

- **сидом в конфиге** (`api-keys.seeds`) — удобно для первого ключа и
  для воспроизводимых окружений (IaC, docker-compose);
- **в дашборде на странице «Ключи»** — генерация, пауза и возврат из
  паузы; ключ живёт в базе.

У каждого ключа — своё имя, свои окна, своя статистика и свои лимиты.
Много устройств/проектов — отдельный ключ каждому: статистика и лимиты
не смешиваются, а скомпрометированный ключ паузится индивидуально.

## Окна и лимиты

Окно — учётный интервал (по умолчанию 5 часов, `window-hours`), который
ключ не может покинуть: если запрос начался в окне N, он доедет в нём
даже после смены окна. Лимиты задаются на ключ на окно:

- `cost-usd-limit` — потолок расходов;
- `requests-limit` — потолок числа запросов;
- `overdraft-usd-limit` — разрешённый перерасход на длинных стримах
  (стоимость известна только по завершении стрима).

При исчерпании лимита ключ получает ошибку протокола с понятным
сообщением, в дашборде это видно сразу. Долгий подряд идущий стрим не
рубится посередине — перерасход покрывается овердрафтом.

## Провайдеры, модели, роутинг

Провайдер = тип (`anthropic` / `openai`) + `base-url` + ключ + список
моделей. Модель описана парой имён: `public` (как её видят клиенты) и
`upstream` (как её зовёт провайдер). Клиент всегда просит по `public`
имени.

В `allow` перечисляются модели, разрешённые через провайдера; всё, что
не в списке, уходит дальше по цепочке — так один «широкий» провайдер
(например, OpenRouter) можно оставить запасным для длинного хвоста
моделей.

Полезные механизмы:

- **sticky-аффинитет** (`sticky-ttl`): в пределах TTL запросы одного
  ключа к одной модели попадают на того же провайдера — это повышает
  шанс попадания в серверный кэш промптов и снижает расход;
- **кулдаун**: провайдер, вернувший ошибку, временно исключается из
  роутинга, запрос уходит к следующему;
- **переопределение на ключ**: на дашборде можно закрепить за ключом
  конкретного провайдера поверх автоматического роутинга.

## Экономия токенов

Три независимых механизма, включаются в конфиге:

- **Sticky-аффинитет** — см. выше; выравнивает серверный кэш промптов.
- **Кэш запросов** (`proxy-cache`): идентичные повторные запросы
  отдаются из кэша, не тратя токены провайдера.
- **Оптимизатор старых tool_result** (`token-optimizer`): чинит
  устаревшие кэш-маркеры Claude Code — иначе сломанная кэш-подсказка
  заставляет перечитывать историю целиком.

Срез «Экономия» на дашборде показывает, сколько потрачено и сколько
сэкономлено каждым механизмом.

## Дашборд

Открывается на корне прокси (`http://localhost:8080`), если собран
(нужен Node.js на этапе сборки). Основное:

- **Обзор** — что происходит сейчас: активные ключи, текущие окна,
  последние события;
- **Окна** — история окон по ключам: расходы, лимиты, остатки;
- **Экономия** — потрачено/сэкономлено по механизмам;
- **Playground** — отправить запрос в прокси из браузера с выбором
  модели и ключа: удобно проверять настройки провайдеров без клиента;
- **События** — серверный журнал: ошибки провайдеров, кулдауны,
  исчерпание лимитов, падения стримов.

## Эксплуатация

- **SQLite**: база `data/claudeproxy.db` рядом с местом запуска. Для
  бэкапа остановите прокси и скопируйте файл (или используйте
  бэкап-инструмент для «горячего» файла — но атомарность гарантирует
  только остановка).
- **PostgreSQL**: для длительной эксплуатации переключите datasource
  на Postgres — пример в `docker-compose.postgres.yml`. Миграции
  применяются автоматически.
- **Обновление**: обновите рабочую копию, пересоберите jar, перезапустите
  прокси — миграции базы доведут схему до актуальной версии.
- **Куда ставится обновление конфига**: `config/application.yml` читается
  рядом с jar при старте; переменные окружения переопределяют файл.
