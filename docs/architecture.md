# Архитектура claudeproxy

Документ описывает устройство прокси: модули, путь запроса, маршрутизацию,
перевод протоколов и подсистемы. Руководства по запуску — [README](../README.md),
справочник настроек — [settings.md](settings.md), список эндпоинтов — [api.md](api.md).

## Общий вид

```text
Claude Code / SDK ──Anthropic API──▶ claudeproxy (Kotlin, Spring WebFlux)
OpenAI SDK ────────OpenAI API─────▶        │
                                           │  auth ▶ модель-роутинг ▶ перевод протокола
                                           │  учёт токенов ▶ SQLite / PostgreSQL
                                           ├─▶ Anthropic-совместимые (pass-through)
                                           ├─▶ OpenAI-совместимые (перевод Claude↔OpenAI)
                                           │        └─ каждый провайдер — напрямую
                                           │          или через свой прокси/туннель (M31)
                                           └─▶ /api + дашборд (React + TS)
```

Стек: **Kotlin 2.3 + Spring Boot 4.1 WebFlux** (реактивность на корутинах и
Flow, SSE-стриминг без блокировки потоков и без агрегации тел), **SQLite**
(JDBC на выделенном однопоточном диспетчере) или **PostgreSQL**,
**kotlin-logging** поверх SLF4J/Logback, дашборд — **React + TypeScript +
Vite + Recharts**.

## Модули (multi-module Gradle)

Зависимости — строго вниз по списку, циклов нет:

| Модуль | Содержимое |
| --- | --- |
| `model` | контракты без логики: `ProxyProperties`, `UsageEvent`, `ServerEvent`, типы ошибок протокола |
| `database` | доступ к БД, миграции (`database/src/main/resources/db/migration/{sqlite,postgres}`), бэкапы SQLite |
| `service` | бизнес-сервисы: auth, chat, providers, routing, serverevent, usage, proxy/cache, оптимизатор |
| `proxy` | ядро проксирования: контроллеры `/v1/*`, обработчики, перевод Claude↔OpenAI |
| `api` | REST дашборда (`/api/*`) |
| `app` | точка входа, вся конфигурация, пайплайн сборки дашборда, все тесты |

Пакеты `ru.wizard.web.claudeproxy.*` не привязаны к модулям: один пакет может
существовать в нескольких модулях, компонент-скан приложения находит бины по
всему classpath. Сервисный паттерн: интерфейс в пакете, реализация — в
подпакете `impl` (например, `ApiKeyService` + `auth/impl/JdbcApiKeyService`).
Доступ к БД — только через `DatabaseProvider`.

## Путь запроса `/v1/messages`

1. **ApiKeyAuthFilter** (WebFilter): извлекает ключ из `x-api-key` или
   `Authorization: Bearer`, проверяет SHA-256-хэш по БД, кладёт имя ключа в
   атрибут exchange. Все `/v1/*` требуют ключ; дашборд `/api/*` — по Basic
   Auth, если настроен.
2. **ModelRegistry → маршрутизация**: публичное имя модели разворачивается в
   список маршрутов (провайдер + upstream-имя), отсортированных по
   приоритету; внутри приоритета — round-robin. Учитываются sticky-привязка
   разговора, кулдауны провайдеров и лимиты.
3. **Обработчик** (`WebClientAnthropicHandler` / `WebClientOpenAiHandler`):
   - anthropic-провайдер — прозрачный pass-through (с коррекцией системных
     сообщений «в середине разговора»);
   - openai-провайдер — полный перевод Claude→OpenAI и обратно, включая
     SSE-стриминг и tool calls;
   - перед отправкой применяются оверрайды провайдера
     (`ProviderRequestAdjuster`: extra-заголовки, таймауты, режим стрима) и,
     если включён оптимизатор, — сжатие старых `tool_result` (M30).
4. **Исходящий WebClient** строится фабрикой `UpstreamWebClientFactory`:
   без прокси — общий прямой клиент; с привязанным `proxy_endpoint` (M31) —
   клиент с CONNECT-туннелем/SOCKS. У клиента есть таймауты: установка
   соединения и «тишина» апстрима (см. [settings.md](settings.md)).
5. **Retry/fallback**: повторимые ошибки (сеть, 429/5xx) ретраятся на
   том же провайдере, затем прокси переключается на следующий маршрут —
   для стриминга только до первого события клиенту. Провайдер после ошибок
   уходит в кулдаун (`RouteCircuitBreaker`).
6. **Учёт**: `SseUsageSniffer`/`UsageAccumulator` собирают usage из ответа,
   `AsyncUsageRecorder` асинхронно пишет `usage_event` (модель, провайдер,
   токены, длительность, статус/ошибка).

## Маршрутизация и отказоустойчивость

- **Приоритеты**: одна модель — от нескольких провайдеров; меньше приоритет =
  выше позиция. Равные приоритеты чередуются round-robin (`RoundRobinRouteRotator`).
- **Fallback**: при quota exceeded / 5xx / сетевых ошибках — следующий маршрут;
  попытки видны в отчёте `/api/fallback-report`.
- **Кулдауны**: после ошибок провайдер временно исключается из ротации
  (`InMemoryRouteCircuitBreaker`, пороги и окно — настройки каталога
  `ProviderSettingCatalog`).
- **Sticky-аффинность** (по умолчанию выкл.): разговор с общим началом
  (system + tools + первое сообщение) продолжается на том же провайдере из
  равнозначных — сохраняется промпт-кэш апстрима. Привязки in-memory с TTL;
  при фейловере разговор перепривязывается. Диагностика —
  `/api/conversation-affinity-stats`.

## Кэш запросов (L1/L2)

Идемпотентные запросы кэшируются по SHA-256 канонического JSON тела
(`CanonicalJsonSerializer`): нестриминговые ответы — JSON, стриминговые —
SSE-поток собирается (`JsonFromSseAssembler`) и при попадании
воспроизводится (`SseFromJsonSynthesizer`). TTL — 5 минут / 1 час
(prompt/prefix-уровни). Лимит строк — LRU. Диагностика —
`/api/request-cache-stats`.

## Оптимизатор токенов (M30)

Опциональный модель-оптимизатор сжимает старые `tool_result` в истории,
когда символов больше порога: батч-вызов к назначенной модели с маркерами,
LRU-кэш по SHA-256 контента (повторы не дёргают модель), single-flight,
breaker (3 отказа → пауза). Экономия считается как
`(символы до − после) / 4` и пишется в usage; расход модели-оптимизатора —
в `/api/optimizer/stats`, а не в usage чатов. Настройки — глобальный
конфиг + до-16 точечных оверрайдов на провайдера (`SET-*` из
`ProviderSettingCatalog`, видны и редактируются в форме провайдера).

## Прокси-эндпоинты (M31)

Таблица `proxy_endpoint`: HTTP/HTTPS (CONNECT-туннель) или SOCKS4/5,
логин/пароль (пароль поддерживает `${ENV:...}`). Провайдер ссылается на
прокси по имени (`provider.proxy_name`); всё исходящее провайдера — чат,
batches/files, discovery моделей, OAuth-токен, оптимизатор — идёт через
него. Выключенный прокси не используется (прямое соединение). Проверка
связности — кнопка «Проверить» на странице «Прокси» (`POST /api/proxies/{id}/check`).

## Прочие подсистемы

- **5-часовые окна**: у каждого клиентского ключа свой цикл «как лимиты
  подписки Claude»; дашборд показывает текущее окно, историю и итоги
  недели/месяца. Аналогичные окна считаются и по провайдерам (выработка
  против информационных лимитов).
- **Калибровка count_tokens** (openai): коэффициент «символы → токены»
  дообучается по фактическим `input_tokens` ответов; применяется, когда
  набралось достаточно образцов. Сброс — `DELETE /api/token-calibration`.
- **Журнал событий сервера**: WARN/ERROR из логов (Logback-апендер) и явные
  события (старт/стоп, кулдауны, фолбэки) пишутся асинхронно в `server_event`
  с ретеншеном; страница «События» с фильтрами.
- **Бэкапы SQLite**: `VACUUM INTO` по cron без остановки записи, хранение N
  последних копий (для PostgreSQL неактивно — используйте `pg_dump`).
- **Дашборд**: собирается `npm run build` и копируется в jar задачами
  `buildDashboard`/`copyDashboardIntoJar`; раздаётся бэкендом на `/`.

## База данных

SQLite (по умолчанию, файл `data/claudeproxy.db`, доступ сериализован через
`Dispatchers.IO.limitedParallelism(1)`) или внешний PostgreSQL (диалект
выбирается по JDBC-URL). Миграции Flyway-формата применяются при старте
автоматически; наборы по диалектам лежат в
`database/src/main/resources/db/migration/{sqlite,postgres}/V*.sql`.
Основные таблицы: `api_key` (SHA-256-хэши), `provider`, `model`,
`usage_event`, `client_window`/`provider_window`, `error_detail`,
`chat_*`, `request_cache`, `token_calibration`, `optimizer_config`,
`server_event`, `proxy_endpoint`.
